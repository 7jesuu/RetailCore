# Трансформация и целевая архитектура первого этапа — RetailCore

## 0. Паспорт документа

- **Название проекта:** RetailCore — управляемая трансформация платформы заказов
- **Бизнес-сценарий:** Повышение управляемости и прозрачности order flow + подготовка к новым коммерческим сценариям
- **Горизонт целевой архитектуры:** Первый этап (3–6 месяцев) — промежуточное состояние
- **Связанные документы:** Architecture Canvas, AS-IS Context, requirements, stakeholders, interview-analysis

## 1. Краткое резюме трансформации

В рамках проекта RetailCore система должна ускорить вывод коммерческих изменений, повысить прозрачность состояния заказа и снизить долю ручных операций, сохраняя непрерывность бизнеса.  
В текущем состоянии этому мешают: высокая связность Java-монолита и Oracle, размазанная логика статусов и промо, отсутствие канонической модели заказа, смешанные интеграции (в т.ч. через staging-таблицы) и нагрузка аналитики на операционную БД.  

Для первого этапа выбраны точки трансформации с приемлемым риском:
1. Введение канонической модели событий и статусов заказа (read-model + event stream).
2. Стабилизация и унификация слоя логистических интеграций (события вместо части обмена через БД).
3. Выделение operational view состояния заказа для поддержки и внутренних команд.
4. Снижение прямой аналитической нагрузки на операционную Oracle.

Целевая архитектура **не** заменяет монолит и не трогает критический путь create order + payment orchestration. Она изолирует чтение статусов, часть post-order processing и интеграции, вводит события и согласованный read-model, позволяя проверять эффект по метрикам прозрачности, ручных операций и нагрузки.

## 2. Бизнес-цель и критерии успеха

**Бизнес-цель:**  
Сделать order flow более прозрачным и управляемым, снизить зависимость от ручных обходов и подготовить безопасный контур для дальнейших изменений (промо, каналы, новые сервисы), не останавливая бизнес.

**Пользовательская ценность:**  
Клиент и оператор поддержки видят согласованное и понятное состояние заказа.

**Операционный эффект:**  
Меньше эскалаций, меньше ручных разборов, более предсказуемое поведение на пиках, единые цифры для бизнеса.

**Горизонт проверки:**  
3–6 месяцев (после внедрения первых точек).

**Ограничения результата первого этапа:**  
Не обещаем полную замену checkout, отказ от Oracle, полную унификацию всех каналов и промо-логики.

### Метрики успеха (целевые ориентиры первого этапа)

- Доля заказов, по которым поддержка получает целостную картину без обращения в смежные команды → рост.
- Среднее время разбора «непонятного статуса» → снижение.
- Количество ручных переводов статусов / эскалаций по зависшим заказам → снижение.
- Доля аналитических запросов, идущих напрямую в операционную Oracle → снижение.
- Количество инцидентов, связанных с рассинхроном статусов на пиках → снижение.
- Lead time типовых изменений в зоне статусов/интеграций (не в core create) → снижение.

(Конкретные числовые baseline нужно уточнить у поддержки, аналитики и эксплуатации.)

## 3. Препятствия AS-IS (связанные с выбранными точками)

- Статусы размазаны по монолиту, платёжному модулю, batch, логистике и ручным действиям поддержки → клиент и оператор видят разные картины.
- Нет канонической модели заказа → «разные цифры» у маркетинга, финансов и операций.
- Логистические интеграции неоднородны (REST + queue + table + batch) + обмен через staging → сложность диагностики и дубли.
- Аналитика читает операционную Oracle напрямую → нагрузка на критический путь.
- Высокая связность create order не позволяет безопасно трогать ядро в первом этапе.

## 4. Точки трансформации

### Точка 1. Каноническая модель событий и статусов заказа (Order Events + Status Read Model)

**Проблема AS-IS:**  
Формальный lifecycle существует, но реальное поведение богаче. Логика переходов размазана. Поддержка и аналитика собирают картину из нескольких источников.

**Бизнес-влияние:**  
Непрозрачность → обращения в поддержку, эскалации, потеря доверия клиента, «разные цифры».

**Ограничение:**  
Нельзя менять критический путь create order и payment orchestration.

**Изменение:**  
- Ввести поток доменных событий заказа (OrderCreated, StatusChanged, DeliveryReserved, PaymentSessionCreated, PartialCancelled и т.д.).
- Построить Status Read Model (отдельное хранилище/проекция), который агрегирует актуальное состояние для поддержки, ЛК и аналитики.
- Монолит и существующие сервисы начинают публиковать события (постепенно, через outbox или аналогичный механизм рядом с текущими обновлениями статусов).

**Что не делаем:**  
Не переписываем внутренние статусы монолита и не меняем транзакцию create order.

**Метрика проверки:**  
- % заказов, для которых operational view совпадает с реальностью (выборочный аудит).
- Снижение обращений «не понимаю статус».
- Снижение ручных эскалаций по зависшим статусам.

**Риски:**  
Неполный охват событий на старте; рассинхрон при ручных вмешательствах.  
Митигация: начать с самых частых переходов + dual-write / сверка.

**Следующий шаг:**  
Согласовать минимальный набор канонических статусов и событий с командой заказов, поддержкой и логистикой.

### Точка 2. Стабилизация слоя логистических интеграций

**Проблема AS-IS:**  
Нет единого контура. Смесь протоколов + staging-таблицы + разная семантика доставки сообщений → дубли, задержки подтверждений, ручной разбор.

**Бизнес-влияние:**  
Изменение обещанного срока доставки после оформления, зависшие статусы, нагрузка на поддержку.

**Ограничение:**  
Нельзя одномоментно переписать все партнёрские интеграции.

**Изменение:**  
- Ввести единый контракт события/статуса доставки.
- Постепенно перевести наиболее проблемные интеграции с обмена через таблицы на события/очередь.
- Добавить идемпотентность и явную семантику ретраев.
- Сохранить антикоррупционный слой к существующим партнёрам.

**Что не делаем:**  
Не трогаем логику выбора маршрута внутри монолита на первом этапе.

**Метрика проверки:**  
- Доля логистических обновлений, приходящих через новый контур.
- Количество дублей заявок / ручных разборов по логистике.
- P95 времени появления подтверждённого статуса доставки в read-model.

**Риски:**  
Потеря сообщений при переходе; несовместимость с конкретным партнёром.  
Митигация: параллельная работа старого и нового контура + feature-flag по партнёрам.

### Точка 3. Operational View состояния заказа для поддержки

**Проблема AS-IS:**  
Карточка заказа не является единым источником правды. Оператор ходит по нескольким системам.

**Бизнес-влияние:**  
Рост времени обработки обращений, особенно на пиках и в сложных сценариях.

**Изменение:**  
- На базе Status Read Model сделать operational view (API + UI/интеграция в существующие инструменты поддержки).
- Показывать согласованный статус, ключевые события, причину задержки (если известна), ссылки на связанные сущности.

**Что не делаем:**  
Не заменяем все админ-инструменты и не убираем возможность ручного вмешательства (пока).

**Метрика проверки:**  
- Среднее время до первого ответа / до решения по обращениям «статус».
- % обращений, закрытых первой линией без эскалации.

### Точка 4. Снижение аналитической нагрузки на операционную Oracle

**Проблема AS-IS:**  
Тяжёлые выборки и пайплайны бьют по операционной БД.

**Изменение:**  
- Перевести приоритетные отчёты на чтение из Status Read Model / отдельного аналитического хранилища, наполняемого событиями.
- Ограничить прямые тяжёлые SQL в пиковые окна.

**Метрика проверки:**  
- Доля аналитического трафика, идущего мимо операционной Oracle.
- Влияние на latency checkout в пиках (косвенно).

## 5. Что сознательно не трогаем в первом этапе (и почему)

| Элемент | Почему важен | Почему не сейчас | Как учитывать дальше |
|---------|--------------|------------------|----------------------|
| Core create order + длинная транзакция | Критический путь выручки | Слишком высокая связность и риск | После появления событий и read-model |
| Полная замена промо-логики | Много исключений и fallback | Высокий бизнес-риск | Отдельный этап после стабилизации статусов |
| Отказ от Oracle / миграция данных | Импортонезависимость | Нет окна и слишком большой объём | Долгосрочная программа |
| Полная унификация всех каналов | Разные ветки сейчас | Требует глубокого рефакторинга ядра | После выделения order model |
| Переписывание всех логистических партнёров | Много исключений | Нереалистично за один этап | По одному партнёру через новый контур |

## 6. Целевая архитектура первого этапа (TO-BE)

### Краткое описание

- **Монолит** остаётся оркестратором create order, payment session и базового резерва доставки.
- Рядом с обновлениями статусов монолит (и ключевые сервисы) публикует **доменные события**.
- Появляется **Order Status Read Model** (проекция) — единый источник правды для поддержки, части ЛК и аналитики.
- **Logistics Integration Layer** начинает принимать и отдавать события по единому контракту; часть staging-обмена постепенно выводится.
- **Analytics** читает преимущественно из read-model / event-хранилища, а не напрямую из операционной Oracle.
- **Support Tools** получают operational view на базе read-model.
- Критический путь create order **не меняется** по транзакционным границам.

### Границы

**Входит в первый этап:**
- События заказа и статусов
- Status Read Model
- Operational view для поддержки
- Унификация части логистических интеграций
- Снижение прямой аналитической нагрузки

**Не входит:**
- Переписывание create order
- Замена Oracle
- Полная замена промо и канальной логики
- Изменение платёжного orchestration

### Основной сценарий (успешный поток)

1. Клиент оформляет заказ → монолит (как сейчас).
2. Монолит сохраняет заказ, вызывает promo/payment/delivery (как сейчас).
3. При каждом значимом изменении статуса/состояния публикуется событие.
4. Read Model обновляется.
5. Поддержка и аналитика читают согласованное состояние из Read Model.
6. Логистические обновления по новым/переведённым партнёрам приходят через единый интеграционный слой.

### Компоненты первого этапа

- Java-монолит (без изменения core create)
- Oracle (операционная)
- Order Event Publisher (новый тонкий слой / outbox)
- Order Status Read Model (новое хранилище/сервис)
- Logistics Integration Layer (эволюционирующий)
- Analytics (переключение источников)
- Support Operational View

## 7. Приоритизация

1. **Канонические события + Status Read Model** — основа прозрачности и всех последующих шагов.
2. **Operational View для поддержки** — быстрый бизнес-эффект и проверка качества событий.
3. **Стабилизация логистических интеграций** (начиная с 1–2 самых проблемных партнёров).
4. **Переключение аналитики** на read-model / события.

## 8. Связь с ограничениями и рисками

- Все изменения — рядом с существующим потоком (strangler / parallel run), а не вместо него.
- Критический путь create order + payment не разрывается.
- Можно включать по каналу / партнёру / проценту трафика.
- Есть возможность сверки старого и нового представления состояния.
