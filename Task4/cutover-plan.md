# Cutover Plan — переход на Order Status Read Model как основной источник правды для поддержки (Этап 2)

## 1. Цель переключения
Сделать Order Status Read Model основным источником актуального состояния заказа для операторов поддержки (Operational View), сохранив возможность быстрого возврата к старым инструментам и не затрагивая критический путь оформления и оплаты заказа.

## 2. Объект переключения
- **Что включаем:** Operational View на базе Read Model как default-экран/источник для работы с состоянием заказа в поддержке.
- **Что не трогаем:**  
  - транзакцию create order в монолите;  
  - payment orchestration;  
  - запись статусов в Oracle/монолит (они остаются source of truth для записи);  
  - логику выбора маршрута и промо.

## 3. Предварительные условия (Entry Criteria)

### Технические
- Этап 1 завершён: события публикуются, Read Model строится, сверка на пилоте показала ≥ 95% согласованности по согласованным правилам.
- Дашборды наблюдаемости работают:  
  - латентность появления события в Read Model;  
  - количество и процент расхождений;  
  - ошибки публикации/потребления.
- Feature-flag / конфигурация, позволяющая мгновенно вернуть поддержку на старый view.
- Проведено нагрузочное тестирование Read Model на объёме, сопоставимом с пиковым.
- Логи и корреляционные ID позволяют быстро найти заказ в обоих контурах.

### Данные
- Правила маппинга статусов и обработки ручных вмешательств согласованы.
- Есть процедура сверки выборки заказов (автоматическая + выборочная ручная).

### Организационные
- Поддержка обучена новому Operational View и знает, как эскалировать расхождения.
- Назначены роли на время cutover (см. ниже).
- Коммуникация с бизнесом и поддержкой проведена (когда включаем, что делать при проблемах).
- Определено окно переключения (предпочтительно низкая нагрузка + присутствие ключевых людей).

## 4. Роли и ответственность

| Роль | Ответственность |
|------|-----------------|
| Техлид монолита / владелец publisher | Состояние публикации событий, быстрый rollback флага |
| Владелец Read Model | Здоровье проекции, сверка, производительность |
| Руководитель поддержки (или тимлид) | Готовность операторов, сбор обратной связи, решение об эскалации |
| Дежурный архитектор / tech lead миграции | Общая координация cutover, решение go/no-go и rollback |
| Эксплуатация / SRE | Мониторинг инфраструктуры, алерты |
| Представитель бизнеса (по необходимости) | Подтверждение приемлемости с точки зрения клиентского опыта |

## 5. Пошаговый сценарий cutover

### T-24h / T-12h
1. Финальная проверка Entry Criteria.
2. Уведомление поддержки и заинтересованных команд.
3. Проверка дашбордов и алертов.
4. Убедиться, что rollback-процедура протестирована (хотя бы на staging).

### T-0 (начало окна)
1. Ещё раз снять baseline метрик (расхождения, латентность, количество открытых обращений по статусам).
2. Включить Operational View как default для ограниченной группы операторов (canary 10–20%) **или** сразу для всего потока, если пилот уже доказал стабильность (решение фиксируется заранее).
3. Начать усиленный мониторинг:
   - расхождения Read Model vs монолит/Oracle;
   - ошибки API Operational View;
   - обратная связь от операторов в специальном канале;
   - изменение времени обработки обращений.

### T+30 мин / T+1–2 часа
4. Короткий статус-синк: есть ли критичные расхождения или жалобы операторов.
5. Если canary — решение о расширении процента.
6. Фиксация всех найденных расхождений в журнале (даже если они не блокирующие).

### T+4–8 часов (или конец рабочего дня)
7. Оценка по критериям успеха (см. ниже).
8. Решение:
   - **Оставить** новый view как default;
   - **Расширить** canary;
   - **Откатить**.

### T+24–48 часов
9. Повторная оценка метрик и обратной связи.
10. Закрытие cutover-отчёта.

## 6. Проверки после переключения (Success Criteria)

**Обязательные (блокирующие rollback, если не выполнены):**
- Нет роста критичных инцидентов, связанных с отображением статуса.
- Read Model доступен (error rate и latency в допустимых пределах).
- Процент расхождений не превышает согласованный порог (например, < 5% по пилотным правилам, точное значение фиксируется до cutover).

**Желательные:**
- Операторы подтверждают, что в большинстве случаев картина достаточна для ответа клиенту.
- Нет резкого роста среднего времени обработки обращений по статусу.
- Количество эскалаций «не видим статус» не выросло.

**Проверка данных:**
- Выборочная сверка 50–100 заказов разных типов (обычный, маркетплейс, частичная отмена, зависший, с ручным вмешательством).
- Сверка особенно важна для заказов, по которым поддержка уже открыла обращение.

## 7. Rollback-сценарий

**Триггеры rollback (любой из):**
- Процент расхождений превышает порог и не снижается.
- Read Model или Operational View API деградировали (высокая ошибка/латентность).
- Массовые жалобы операторов, что картина неполная или вводит в заблуждение.
- Появление инцидентов, напрямую связанных с новым view и влияющих на клиентов.

**Действия rollback (цель — < 5–10 минут):**
1. Ответственный за feature-flag переключает поддержку обратно на старый view / старые инструменты.
2. Подтверждение от поддержки, что они снова работают в привычном режиме.
3. Фиксация инцидента и сбор логов/расхождений для анализа.
4. Коммуникация: «временно вернулись на предыдущий режим, разбираем причины».
5. Критический путь заказа (create / payment / logistics) **не затрагивается** rollback’ом.

**После rollback:**
- Анализ причин.
- Исправление (доработка событий, маппинга, обработки ручных статусов).
- Повторный canary только после устранения корневой причины.

## 8. Наблюдаемость и данные во время cutover

Обязательный минимум:
- Метрика латентности события → Read Model.
- Метрика и алерт по расхождениям (заказ в монолите vs Read Model).
- Логи с correlation id заказа.
- Канал быстрой обратной связи от поддержки.
- Дашборд доступности Operational View API.

Рекомендуется также:
- Сэмплирование заказов с ручными вмешательствами.
- Сравнение количества эскалаций «статус» до/после в первые 24–48 часов.

## 9. Коммуникации

- **До:** анонс поддержки и смежных команд (что меняется, куда писать о проблемах, кто принимает решение об откате).
- **Во время:** статус в общем канале каждые 30–60 минут в первые часы.
- **После:** короткий отчёт (успех / частичный успех / rollback + причины + следующие шаги).

## 10. Связь с общим roadmap
Этот cutover соответствует переходу Этапа 1 → Этапа 2.  
Успешное выполнение открывает возможность уверенно двигаться к Этапу 3 (логистические интеграции) и Этапу 4 (аналитика), потому что появляется проверенный единый источник правды о состоянии заказа.
