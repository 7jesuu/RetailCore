# Roadmap миграции RetailCore (первый горизонт 3–9 месяцев)

## Цель roadmap
Обеспечить поэтапный переход от AS-IS к целевому состоянию первого этапа без остановки критичных процессов (оформление заказа, оплата, базовая логистика). Каждый этап имеет проверяемый результат, критерии выхода и возможность отката.

## Принципы миграции
- Strangler Fig / parallel run — новый контур работает рядом со старым.
- Критический путь create order + payment orchestration не разрывается.
- Включение по каналу / партнёру / проценту трафика.
- Обязательная сверка старого и нового представления состояния.
- Сначала прозрачность и наблюдаемость, потом углубление изменений.
- Каждый этап должен давать измеримый бизнес- или операционный эффект.

## Обзор этапов

### Этап 0. Подготовка (2–4 недели)
**Цель:** создать технические и организационные предпосылки.

**Работы:**
- Согласовать минимальный канонический набор статусов и доменных событий с командами заказов, поддержки, логистики и аналитики.
- Выбрать механизм публикации событий (outbox-паттерн рядом с текущими обновлениями статусов в монолите).
- Подготовить инфраструктуру для Order Status Read Model (хранилище + API).
- Настроить базовую наблюдаемость: корреляционный ID заказа, метрики публикации/потребления событий, дашборды расхождений.
- Определить набор заказов/каналов для пилота.

**Промежуточное состояние:**  
Монолит работает как раньше. Инфраструктура событий и Read Model развёрнута, но ещё не влияет на пользователей.

**Зависимости:**  
Доступ к монолиту, согласование модели статусов, инфраструктурные ресурсы.

**Риски:**  
Споры о модели статусов; задержки инфраструктуры.  
Митигация: зафиксировать MVP-набор событий (8–12 ключевых) и не пытаться покрыть все исключения сразу.

**Критерии завершения:**
- Утверждён список канонических событий и статусов.
- Outbox / publisher работает в тестовом контуре.
- Read Model развёрнут и принимает тестовые события.
- Есть дашборд сверки (хотя бы ручной).

### Этап 1. События + Status Read Model (пилот) — 4–6 недель
**Цель:** получить согласованное представление состояния заказа для части потока.

**Работы:**
- Монолит начинает публиковать события при ключевых переходах статусов (dual-write / outbox).
- Read Model строит проекцию состояния.
- Включается сверка: для пилотных заказов сравниваем состояние в монолите/Oracle и в Read Model.
- Поддержка получает доступ к operational view в режиме «только чтение + сравнение» (ещё не основной инструмент).

**Промежуточное состояние:**  
Старый контур — source of truth. Новый контур — тень + сверка. Пользователи и критический путь не затронуты.

**Зависимости:**  
Этап 0.

**Риски:**  
Неполнота событий; рассинхрон при ручных вмешательствах поддержки.  
Митигация: алерт при расхождении + ручная сверка выборки заказов.

**Критерии завершения:**
- ≥ 95% пилотных заказов имеют согласованное состояние в Read Model (по согласованным правилам).
- Среднее время появления события в Read Model приемлемо (целевой ориентир — секунды/минуты, уточняется).
- Нет критичных инцидентов, связанных с публикацией событий.
- Поддержка подтвердила полезность operational view на пилоте.

### Этап 2. Operational View как основной инструмент поддержки — 3–5 недель
**Цель:** дать поддержке единую картину заказа и снизить эскалации.

**Работы:**
- Operational View становится основным экраном для работы с состоянием заказа (с сохранением возможности уйти в старые инструменты).
- Расширяется покрытие событий (добавляются частые исключительные сценарии).
- Вводятся метрики: время разбора «непонятного статуса», доля эскалаций.

**Промежуточное состояние:**  
Read Model — основной источник правды для поддержки. Монолит и Oracle остаются source of truth для записи.

**Зависимости:**  
Этап 1 (качество событий).

**Риски:**  
Неполное покрытие редких статусов → операторы всё равно уходят в старые системы.  
Митигация: явный список покрытых/непокрытых сценариев + быстрый feedback-цикл.

**Критерии завершения:**
- Снижение среднего времени разбора обращений по статусу (целевое значение согласовать с поддержкой).
- Рост доли обращений, закрытых без эскалации в смежные команды.
- Положительная обратная связь от первой линии поддержки.

### Этап 3. Стабилизация логистических интеграций (1–2 партнёра) — 4–7 недель
**Цель:** убрать часть обмена через staging-таблицы и унифицировать статусы доставки.

**Работы:**
- Выбрать 1–2 наиболее проблемных логистических партнёра.
- Ввести единый контракт события статуса доставки.
- Перевести выбранных партнёров на новый контур (параллельно со старым).
- Обеспечить идемпотентность и явную семантику ретраев.
- События доставки начинают питать Read Model.

**Промежуточное состояние:**  
Для выбранных партнёров — dual-run. Для остальных — старый способ.

**Зависимости:**  
Этап 1–2 (события и Read Model уже есть).

**Риски:**  
Дубли заявок; потеря обновлений; особенности конкретного API партнёра.  
Митигация: feature-flag по партнёру, усиленный мониторинг, возможность мгновенного возврата на старый контур.

**Критерии завершения:**
- Для пилотных партнёров доля обновлений через новый контур ≥ 95%.
- Количество дублей / ручных разборов по этим партнёрам снизилось.
- Статусы доставки корректно отражаются в Read Model.

### Этап 4. Снижение аналитической нагрузки на Oracle — 3–5 недель
**Цель:** перевести приоритетные отчёты на Read Model / event-хранилище.

**Работы:**
- Определить топ отчётов, создающих нагрузку.
- Переключить их на чтение из Read Model или отдельного аналитического слоя, наполняемого событиями.
- Ограничить тяжёлые прямые SQL в пиковые окна.

**Промежуточное состояние:**  
Часть аналитики уже на новом источнике, часть ещё на Oracle.

**Зависимости:**  
Качество и полнота событий (Этапы 1–3).

**Риски:**  
Расхождение цифр между старыми и новыми витринами.  
Митигация: параллельный расчёт и сверка в течение переходного периода.

**Критерии завершения:**
- Согласованный список отчётов переведён.
- Зафиксировано снижение доли тяжёлых запросов к операционной Oracle.
- Бизнес подтвердил приемлемость данных новых витрин.

### Этап 5. Оценка и подготовка следующего горизонта
**Цель:** зафиксировать результаты, обновить риски и выбрать следующие точки трансформации (промо, более глубокое выделение order model, следующие партнёры и т.д.).

**Критерии:**
- Отчёт по метрикам всех этапов.
- Обновлённый backlog точек трансформации.
- Решение go/no-go по следующим изменениям критического пути.

## Общие риски roadmap и митигации
- **Неполнота событий** → начинать с MVP-набора + постоянная сверка.
- **Сопротивление поддержкой/бизнеса новым инструментам** → раннее вовлечение и быстрый эффект в Этапе 2.
- **Регрессии в монолите при добавлении publisher** → feature-flag, тщательное тестирование outbox, canary.
- **Нехватка инфраструктуры** → заранее согласовать ресурсы в Этапе 0.
- **Расползание scope** → жёстко держать «что не делаем» (create order, payment orchestration, полный отказ от Oracle).
