# AS-IS Context Diagram — RetailCore

## Текстовое описание контекста

### Внешние участники
- Клиенты (сайт, мобильное приложение)
- Маркетплейсы
- Платёжные провайдеры
- Службы доставки / логистические партнёры
- Склады (внутренние и партнёрские)

### Внутренние основные части системы

**1. Java-монолит (Order Core / Orchestrator)**
- Центральная точка прохождения почти любого заказа.
- Отвечает за: создание заказа, расчёт цены (базовый + канальные/региональные надбавки), вызов/fallback промо, выбор маршрута, резервирование слота доставки, создание платёжной сессии, управление частью статусов, запись в staging-таблицы, прямые SQL.
- Содержит длинные транзакции и высокую связность.

**2. Oracle Database**
- Операционное хранилище заказов, статусов, справочников, правил.
- Содержит критичную бизнес-логику в packages (в т.ч. legacy promo).
- Staging-таблицы для обмена с .NET и другими системами.
- Источник данных для аналитики (прямые SQL и выгрузки).
- Узкое место по производительности и связанности.

**3. Promo Service**
- Внешний/отдельный сервис расчёта скидок.
- Используется не во всех сценариях; при недоступности — fallback в Oracle package.

**4. Payment Gateway / модуль**
- Создание платёжных сессий (синхронно из монолита).
- Часть логики статусов и повторных оплат.

**5. Delivery / Logistics Integrations**
- Смесь: синхронные вызовы, очереди, polling по таблицам, batch, промежуточный .NET-сервис.
- Правила маршрутизации размазаны: монолит + конфиги + Oracle-таблицы + ночные SQL-скрипты.
- Сильная зависимость от атрибутов и статусов, формируемых монолитом.

**6. .NET-сервисы**
- В том числе интеграционный обмен через staging-таблицы Oracle.
- Участвуют в части логистических и вспомогательных сценариев.

**7. Python / Analytics & Reporting**
- Набор пайплайнов: прямые SQL в Oracle, staging, API, CSV, batch.
- Несколько «почти канонических» моделей заказа (операционная, финансовая, маркетинговая).
- Создаёт нагрузку на операционную Oracle.

**8. Support / Admin tools**
- Административные интерфейсы и ручные переводы статусов.
- Компенсация зависших и исключительных сценариев.

### Ключевые потоки данных (упрощённо)

1. Клиент / канал → Монолит (create order)
2. Монолит → Promo Service (или Oracle package fallback)
3. Монолит → Oracle (сохранение заказа, статусы, staging)
4. Монолит → Delivery Gateway (reserve slot, sync)
5. Монолит → Payment Gateway (create session, sync)
6. Монолит / Oracle → .NET (через staging-таблицы)
7. Монолит / Logistics → Внешние службы доставки и склады (разными протоколами)
8. Oracle + выгрузки + API → Analytics pipelines → Витрины отчётов
9. Поддержка → Admin tools → изменение статусов / флаги в монолите/Oracle

### Проблемные зоны и зависимости (на диаграмме стоит явно пометить)

- Монолит как единственный оркестратор критического пути.
- Длинная транзакция оформления, затрагивающая несколько внешних систем и Oracle.
- Логика промо и маршрутизации распределена по коду, конфигам, таблицам и packages.
- Обмен через общую БД (staging) как скрытая интеграция.
- Отсутствие единого события/канонической модели заказа → расхождения в аналитике и статусах.
- Ручные вмешательства поддержки в жизненный цикл.
- Аналитическая нагрузка на операционную Oracle.
